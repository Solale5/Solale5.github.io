The problem

Building for a real vehicle

A vehicle sleeps, readings grow old, and a successful API response does not prove the cabin has cooled. CabinWise brings useful daily actions together while making those limits visible to both a person and an AI assistant.

Engineering decisions

Handling commands with care

Accepted ≠ observed

The gateway can report that Tesla accepted a command. The UI verifies supported settings against a subsequent vehicle reading and its subsystem timestamp. A climate setpoint is never presented as the measured cabin temperature.

If delivery is uncertain, the result stays uncertain. The app does not automatically resend the physical action. MCP request IDs retain results within the active process so a repeated ID cannot silently deliver the same action again.

Waking a sleeping vehicle

Status reads stay passive. A requested command can wake the vehicle once, then check readiness within a bounded wait. The web flow allows up to one minute; it sends the command only when readiness is confirmed in time.

The gateway validates inputs and signed requests, including timestamps and replay checks. These are layered protections, not a claim of exactly-once delivery across restarts or network failures.

  1. Review the actionValidate the requested change and confirm intent.
  2. Prepare the vehicleWake if needed. Wait for readiness within a deadline.
  3. Send the commandTrack acceptance; preserve uncertainty on failure.
  4. Check the readingUse fresh reported state to distinguish a result from an acknowledgement.

Architecture

How it fits together

The browser never receives a raw signing key. Owner checks and encrypted, secure HTTP-only sessions protect the app’s Tesla authorization. A constrained command gateway separates the web experience from the signing service.

A narrow command path

A Node gateway and Tesla signing service run in Docker on DigitalOcean, behind Cloudflare access controls and a tunnel. The gateway checks a separate secret and HMAC request signatures. The raw signer is not publicly exposed.

Permission is temporary

MCP grants separate status, navigation, climate, and charging access. They expire, can be revoked, and are checked for every tool call. Tesla access for MCP stays in process memory, bounded by the grant and session expiry.

Deliberate scope

What it does today

The result is a personal tool for a real vehicle, spanning an interactive frontend, a protected command service, and permission-scoped AI access. Its most important design choice is preserving uncertainty wherever the system cannot verify an outcome.

  • One destination at a time. An ordered stop list lets the owner review and send a selected stop. It does not send a complete multi-stop itinerary, optimize routes, or detect arrivals.
  • Presets are not schedules. Saved departure settings stay in the browser and require an explicit action. Autonomous scheduling is outside the verified scope.
  • No background-telemetry claim. This case study covers requested readings and controls, not continuous vehicle monitoring or a working telemetry history.
  • Private by design. The source and operational app remain private. This page provides an ungated explanation and fictional sample data.
